# SFR-013 전체 영상 추적 구현·검증 기록

작성: 2026-11-27, 한국 시간. 기준 main은 `6cdb4a2299dbd8dc77ba2541dc73f7048b64e8e6`, 작업 브랜치는 `kjh-sfr-013`이다. 이 기록은 커밋 전 로컬 구현 상태를 설명한다.

아래 270개 통과는 후속 P2 리뷰 전의 전체 영상 구현 검증 기록이다. 이후 지적된 세 건의 수정과 최신 회귀·실제 Linux 검증 결과는 [P2 수정 검증 기록](sfr-013-p2-fixes-verification.md)에 별도로 정리한다.

## 구현 범위

영상 등록 길이 상한을 7일에서 **10시간(36,000초)**으로 줄였다. 파일 크기 상한은 **4GiB**를 유지한다. 기존에 등록된 긴 원본은 원본 정보가 그대로일 때 편집 정보를 보존하며, 신규 등록이나 원본 교체에는 새 상한을 적용한다.

SFR-013은 원본 전체를 백그라운드에서 추적한다. 브라우저의 8MiB 재개 가능 업로드, 비공개 원본의 generation 고정, 영속 대기열, 60초 내부 처리 창, 체크포인트, 취소·재개와 결과 창 조회를 연결했다. 내부 경계를 넘을 때 활성 대상과 전역 ID를 이어가며, 영상 마지막까지 처리된 경우에만 완료로 표시한다. 추적 결과는 기존 자막과 수동 크롭을 바꾸지 않는다. SFR-014 자동 크롭은 별도 기능이다.

10시간은 **등록 가능한 영상 길이**다. 분석이 10시간 안에 끝난다는 보장이나 모든 AI 기능의 동일한 지원 한도를 뜻하지 않는다. 기존 STT 경로의 25MiB·1시간 제한은 이번 변경에서 수정하지 않았다.

설계와 API의 기준은 [설계 v2](sfr-013-full-video-spec.md), [전체 추적 계약](../contracts/full-tracking-v2.md), [클라우드 연결과 롤백 안내](full-tracking-cloud-setup.md)다. Agent Skills의 명세·단계별 구현·API 계약 지침을 적용했다.

## 실제 10분 원본의 전체 처리

기존 공개 UCL 표본을 반복해 **600.2초, 87,039,697바이트**의 MP4를 만들었다. 반복 영상이므로 다양한 10분 원본의 정확도를 대표하지는 않는다. 실제 NanoDet 모델, Python 제어 API, 별도 runner 프로세스, Node 인증 API, SQLite와 원본 파일을 연결했다.

| 확인 항목 | 결과 |
|---|---|
| 전체 범위 | 0초부터 600.2초까지 **11개 창** 처리 완료 |
| 취소·재개 | 첫 60초 커밋 뒤 취소, 같은 체크포인트에서 재개 |
| 기존 결과 유지 | 취소 전에 커밋된 결과 창이 재개 후에도 동일함 |
| 마지막 구간 | 600–600.2초 창에 **9개 트랙·9개 관측** 확인 |
| 원본 일치 | 별도 스트리밍 SHA-256 계산과 분석 원본 SHA-256 일치 |
| 선택 복원 | 주요 대상 선택을 저장한 뒤 조회로 복원 |
| 원본 재생 | 인증된 원본 경로에서 임시 재생 URL 연결, HTTP **206 Range** 재생 확인 |
| 로컬 소요 시간 | **92.3초**. 최종 미디어 수정 후 재실행한 해당 PC·표본의 관측값이며 운영 성능 보장이 아님 |

실행 근거는 원래 작업 폴더의 `.cache/sfr013-full-verification/integration-result.json`에 보관한다. 최종 미디어 수정 전의 98.3초 실행은 `integration-before-eof-fix.json`에 별도로 보존했다. 인증 쿠키·비밀번호·서비스 토큰은 이 문서에 포함하지 않는다.

데스크톱 브라우저에서도 저장된 프로젝트를 열어 서버 원본과 중앙 영상 미리보기가 즉시 복원되는 것을 확인했다. 피사체 탭의 전체 완료·11/11구간 표시, 600초 결과 창, 추천 대상 `t3442` 선택 저장과 다시 불러오기 후 선택 복원을 확인했다.

## 실제 브라우저 업로드와 미리보기

컴퓨터 유스로 파일 선택창부터 업로드와 추적 완료까지 조작했다. API 통합 실행과 별개로 실제 브라우저의 파일·업로드·미리보기 연결을 확인한 기록이다.

| 표본 | 확인 결과 |
|---|---|
| 76초·11,044,122바이트 UCL 원본 | 파일 선택창에서 선택, 8MiB 분할 업로드, 실제 모델로 전체 **2/2구간** 완료 |
| 6.12초·895,768바이트 짧은 표본 | 새 파일 업로드 후 중앙·피사체 영상 모두 `version=uploadId`가 연결되고 `readyState=4`, **854×480** 확인 |
| 마지막 표본의 재개 | 정상 영상의 끝 프레임 누락을 수정한 뒤 기존 실패 작업을 재개해 **1/1구간** 전체 완료, 화면 오류 안내 없음 |

짧은 표본은 FFprobe 기준 6.12초이며 기존 UCL 영상을 stream-copy한 파일이다. 처음에는 출력 시간 제한 반올림으로 마지막 표본을 잃어 `INCOMPLETE_VIDEO`로 실패했다. 이를 실제 프레임 수와 EOF 검사에 맞춰 수정했고 같은 저장 원본의 작업을 재개해 확인했다. 브라우저 관측 근거는 `.cache/sfr013-full-verification/browser-result.json`에 보관한다.

## 10시간 경계 검증의 의미

10시간 전체 범위는 결정적 프레임 입력으로 **600개 창·72,000개 관측**을 처리하는 시뮬레이션으로 검증했다. 같은 대상의 `t1` ID가 창 경계를 넘어 유지되고, `processedSeconds=36000`에서 완료되는 것을 확인했다. 이 검증은 청크 순회·상태 크기·ID 연속성 검증이다.

**실제 10시간 미디어의 디코딩·검출·클라우드 처리 시간이나 메모리를 측정한 결과는 아니다.** 4GiB 실제 업로드와 운영 장비의 장시간 처리량은 별도 확인이 남는다.

## 리뷰 문제와 경계 오류 수정

| 문제 | 수정과 검증 |
|---|---|
| 제한 시간 종료 뒤 FFmpeg 자식이 남음 | Windows·Linux 프로세스 트리 종료·회수 경로를 적용했다. 실제 자식·손자 heartbeat 회귀로 함께 종료되는지 확인했다. 제한 시간은 영상 분석 범위와 별개다. |
| 분석 서버 503이 일반 오류로 변환됨 | `ANALYSIS_BUSY`, `MODEL_UNAVAILABLE`과 안전한 오류 응답을 구분하고 `Retry-After`를 유지했다. |
| 로컬 체크섬의 계약 불일치 | `crc32-<8hex>`로 통일해 Python 완료 응답과 Node 검증기가 호환되게 했다. |
| 조기 EOF를 전체 완료로 기록 | 예상 프레임 수를 확인한다. 실제 1초 영상·4초 오디오 표본은 `INCOMPLETE_VIDEO`, 처리 0초로 실패하며 미처리 범위를 커밋하지 않는다. 짧은 마지막 구간의 실제 프레임은 보존한다. |
| 정상 짧은 영상의 마지막 표본 누락 | FFmpeg rawvideo 출력에 `-t`와 프레임 수 제한을 함께 적용해 6.12초 영상의 6.0초 표본이 누락되던 문제를 고쳤다. 출력 종료는 `-frames:v`로 제한하고 실제 EOF·예상 프레임 수 검사는 유지한다. 회귀 2개와 실제 작업 재개로 확인했다. |
| 새 서버 원본의 미리보기 갱신·우선순위 | 업로드 완료 ID를 원본 영상 URL의 버전으로 전달한다. 준비 확인된 서버 원본이 이전 로컬 Blob보다 우선하도록 수정하고 프런트 회귀 3개와 실제 브라우저의 두 미리보기로 확인했다. |
| 영상 시작 전 구간을 추적 결과로 채움 | 전체 추적 probe에서 표시 원점과 영상 시작 차이가 0.25초를 넘으면 `UNSUPPORTED_TIMELINE`으로 거부한다. 오디오 0초·영상 2초 시작 MP4로 확인했다. |
| GCS metadata 조회 뒤 generation 교체 | 최초 metadata 404와 다운로드 중 404/412를 구분하고, 후자는 새 Blob으로 최신 generation을 최대 3회 재조회한다. |
| 빠른 완료와 dispatch 기록의 경합 | CAS 충돌 뒤 실제 종료 상태를 확인해 정상 완료를 dispatch 실패로 바꾸지 않는다. |
| 업로드·대기열 복구 경합 | 미커밋 업로드 꼬리를 잘라 저장 offset으로 복원하고, 취소·재개와 runner 확인이 겹쳐도 대기 작업을 유실하지 않도록 검증했다. |

## 남은 운영 확인과 변경 경계

- 실제 GCS 버킷·IAM·Cloud Run Jobs 자원 생성과 운영 연결은 아직 하지 않았다. 저장소와 실행 어댑터는 구현됐으며 운영 환경 검증은 별도다.
- 이 PC에 Docker 실행 환경이 없어 최종 이미지 빌드는 실행하지 않았다.
- 실제 10시간·4GiB 원본의 처리량, 메모리, 운영 네트워크에서의 장시간 업로드와 복구는 측정하지 않았다.
- COCO 검출 모델의 작은 대상·가림·빠른 움직임에서 오분류와 ID 단절 가능성은 남는다. 전체 영상 처리 지원이 모든 장면의 추적 정확도를 보장하지 않는다.
- 프런트 빌드의 기존 500kB 초과 청크 경고가 남아 있다.

기본 `FULL_TRACKING_ENABLED=0`을 유지한다. 새 운영 경로를 켜거나 데모에 배포하지 않았으며 기존 데모·롤백 자료·README와 원래 작업 폴더의 소스 변경은 유지했다. **커밋·푸시·병합은 하지 않았다.** 커밋은 사용자 승인 후 진행한다.
